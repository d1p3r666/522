# Лабораторная работа: LibreDB Studio и Docker Compose

## Цель и исходное задание

Развернуть оригинальный LibreDB Studio средствами Docker Compose, настроить вход администратора и постоянное хранение данных, проверить запуск и освоить безопасную остановку проекта.

LibreDB Studio — открытая веб-среда для работы с базами данных: запросами, просмотром данных и администрированием можно заниматься через браузер. В этой лабораторной используется готовый образ `ghcr.io/libredb/libredb-studio:latest`; собственное приложение не создаётся. SQLite здесь хранит внутренние данные Studio, а не заменяет все базы данных, к которым можно подключаться через интерфейс.

Работа выполнена по [инструкции преподавателя](https://github.com/rurewa/imfua/blob/main/content/Docker/DockerCompose/LibreDB_Studio.md). Проверенная версия исходного файла: blob `6f8afa933968baf3d47c7ce07c6ce0c0c33de1bb`. Конфигурация Compose воспроизводит его пример. Каталог выделен по заданию; предыдущие лабораторные, включая HomeHub, не изменяются.

## Структура и конфигурация

```text
DockerCompose/LibreDB-Studio/
├── compose.yaml
├── .env.example
├── .gitignore
├── Initialize-Env.ps1
├── README.md
└── .env                 # только локально, исключён из Git
```

`compose.yaml` описывает один сервис `libredb-studio` с таким же именем контейнера:

| Параметр | Значение и назначение |
| --- | --- |
| image | `ghcr.io/libredb/libredb-studio:latest`, оригинальный готовый образ |
| ports | `3000:3000`, порт ПК 3000 направляется на порт приложения 3000 |
| ADMIN_EMAIL | Из `.env`; при отсутствии используется `admin@libredb.org` |
| ADMIN_PASSWORD, JWT_SECRET | Обязательные непустые значения из `.env`; без них Compose отклоняет конфигурацию |
| STORAGE_PROVIDER | `sqlite`, внутреннее хранилище Studio |
| STORAGE_SQLITE_PATH | `/app/data/libredb-storage.db`, файл внутри контейнера |
| volumes | `libredb-data:/app/data`, данные сохраняются отдельно от контейнера |
| restart | `unless-stopped`, автоматический перезапуск, кроме явной остановки |
| healthcheck | `wget --spider -q http://localhost:3000`; интервал 30 с, timeout 10 с, 3 неудачные попытки, start_period 40 с |

`start_period` даёт приложению время на инициализацию: неудачи в этот период не увеличивают счётчик отказов. Проверка HTTP не подтверждает успешный вход администратора — его проверяют отдельно.

Имя тома в Compose — `libredb-data`. Docker обычно создаёт физическое имя `libredb-studio_libredb-data`, добавляя имя проекта. Точное имя можно увидеть через `docker inspect`, как показано ниже.

`.env.example` — публичный шаблон из пяти переменных. Его пароли являются заглушками. `.env` — приватные локальные значения. Скрипт `Initialize-Env.ps1` создаёт `.env` с тремя независимыми случайными значениями (административный пароль, JWT-секрет и пользовательский пароль), каждое из 48 криптографически случайных байтов, записанных в Base64 длиной 64 символа. Существующий `.env` скрипт не перезаписывает и секреты в консоль не выводит.

`USER_EMAIL` и `USER_PASSWORD` сохранены в шаблоне по заданию, но не передаются контейнеру: в примере преподавателя они не подключены к сервису. Наличие этих строк в `.env` само по себе не создаёт обычного пользователя. Для лабораторной используется администратор.

## Подготовка Windows и VS Code

1. Установите Git, VS Code и [Docker Desktop для Windows](https://docs.docker.com/desktop/setup/install/windows-install/). Для варианта с WSL 2 включите виртуализацию и подготовьте WSL 2 согласно официальной инструкции. Если установка требует перезагрузки, выполните её.
2. Запустите Docker Desktop и дождитесь готовности движка. Используйте Linux containers. Окно установленной программы и доступный `docker.exe` ещё не означают, что движок работает.
3. Откройте репозиторий `522` в VS Code. Выберите **Terminal → New Terminal**, профиль **PowerShell**.
4. Проверьте инструменты:

```powershell
docker version
docker compose version
```

`docker version` должен показать также секцию Server. Ошибка о `dockerDesktopLinuxEngine` означает, что движок недоступен: сначала исправьте запуск Docker Desktop. Команда `docker compose version` показывает версию клиента Compose.

Если репозиторий ещё не скачан, выполните в каталоге для учебных проектов:

```powershell
git clone https://github.com/d1p3r666/522.git
Set-Location .\522
git switch lab/libredb-studio
```

Если репозиторий уже скачан, сохраните свои незакоммиченные изменения перед переключением ветки, затем выполните из корня репозитория:

```powershell
git fetch origin
git switch lab/libredb-studio
```

После слияния Pull Request можно использовать обновлённую `main`.

## Последовательный запуск

Выполняйте команды по одной. При ошибке устраните её перед следующим шагом.

### 1. Проверить существующие проекты и перейти в каталог

```powershell
docker compose ls
Set-Location .\DockerCompose\LibreDB-Studio
```

Первая команда показывает уже запущенные Compose-проекты. Вторая выбирает каталог лабораторной, чтобы Compose прочитал нужные `compose.yaml` и `.env`.

### 2. Создать приватные переменные

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Initialize-Env.ps1
```

Параметр `ExecutionPolicy` действует на этот процесс PowerShell. Глобальные настройки политики не меняются. На ПК, где работа уже подготовлена, скрипт сохранит существующий `.env`.

Альтернатива: скопируйте `.env.example` в `.env`, только если `.env` ещё отсутствует, и замените все три заглушки секретов собственными случайными значениями. JWT_SECRET должен содержать не менее 32 символов. Не используйте демонстрационные пароли из задания.

Откройте `.env` локально в редакторе, если нужно узнать реквизиты или изменить email. Не публикуйте файл, не включайте его в скриншоты, README и отчёты. Переменные текущего процесса PowerShell имеют приоритет над `.env`; не задавайте там старые `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `JWT_SECRET`.

### 3. Проверить порт и имя контейнера

```powershell
Get-NetTCPConnection -State Listen -ErrorAction Stop | Where-Object LocalPort -eq 3000
docker ps -a --filter 'name=^/libredb-studio$'
```

Первая команда — эквивалент проверки `ss`/`grep`: отсутствие строк при успешном выполнении означает, что слушатель порта 3000 не найден. При отказе в доступе используйте терминал с нужными правами или `netstat -ano -p tcp` и найдите локальный порт 3000 со статусом LISTENING. Вторая команда проверяет и остановленные контейнеры с точным именем `libredb-studio`.

Если порт занят, определите владельца по `OwningProcess` (`Get-Process -Id <PID>`). Если имя занято, выясните, к какому проекту относится контейнер. Не останавливайте и не удаляйте чужие проекты. Безопасное решение — согласовать освобождение порта/имени владельцем либо выполнить лабораторную на другом ПК; исходная конфигурация сохраняет обязательный порт 3000.

### 4. Проверить конфигурацию и запустить сервис

```powershell
docker compose config --quiet
docker compose up -d
```

Первая команда разбирает YAML и проверяет подстановку обязательных переменных. Это безопасный вариант `docker compose config`: обычный вывод полной конфигурации содержит пароли, поэтому его нельзя прикладывать к отчёту или логировать. Compose проверяет наличие JWT_SECRET, но сам по себе не проверяет минимальную длину — её обеспечивает генератор.

Вторая команда при необходимости скачивает оригинальный образ, создаёт сеть, том и контейнер, затем запускает приложение в фоне. Для первой загрузки нужен доступ к `ghcr.io`. Тег `latest` может обновляться со временем.

### 5. Проверить статус и логи

```powershell
docker compose ls
docker compose logs --tail=20 libredb-studio
docker compose ps -a
docker compose logs -f
```

`ls` показывает Compose-проект; `logs --tail=20` — последние 20 строк логов сервиса; `ps -a` — состояние контейнера, включая остановленный; `logs -f` — новые события в реальном времени. Нажмите **Ctrl+C**, чтобы завершить просмотр логов: контейнер продолжит работать.

Затем прочитайте все доступные логи:

```powershell
docker compose logs
```

Проверьте отсутствие ошибок инициализации, доступа к SQLite и аварийного завершения. Перед публикацией логов убедитесь, что они не содержат чувствительных данных.

### 6. Проверить HTTP, healthcheck и том

```powershell
(Invoke-WebRequest -Uri http://localhost:3000 -UseBasicParsing -TimeoutSec 10).StatusCode
docker inspect libredb-studio --format '{{.State.Status}} / {{.State.Health.Status}}'
docker inspect libredb-studio --format '{{json .State.Health}}'
docker inspect libredb-studio --format '{{range .Mounts}}{{println .Type .Name .Destination}}{{end}}'
docker volume ls --filter name=libredb
```

Ожидаются HTTP 200 (в том числе после перехода на страницу входа), состояние `running / healthy`, mount типа `volume` с назначением `/app/data`. Сразу после запуска допустимо `starting`; дождитесь проверок с интервалом 30 с. При `unhealthy` изучите результаты `.State.Health` и логи, затем исправьте причину. Сам факт наличия тома в списке не доказывает его подключение — это подтверждает `.Mounts`.

## Веб-интерфейс и вход администратора

Откройте [http://localhost:3000](http://localhost:3000) в браузере на том же ПК. Введите email из `ADMIN_EMAIL` (по умолчанию `admin@libredb.org`) и пароль из `ADMIN_PASSWORD` вашего локального `.env`. Пароль в репозиторий не включён. Успешный вход должен открыть рабочий интерфейс Studio; один HTTP-ответ без входа этого не доказывает.

При проблемах со входом проверьте выбранный каталог проекта, значения `.env` и логи. Не удаляйте том для «сброса» доступа: в нём находятся данные. Не считайте, что изменение `.env` обязательно меняет уже сохранённые учётные записи.

## Безопасная остановка и удаление

Для остановки с сохранением контейнера и данных:

```powershell
docker compose stop
```

Возобновление — `docker compose start`. Для удаления контейнера и сети с сохранением именованного тома используйте `docker compose down`; последующий `docker compose up -d` снова подключит том.

Следующие команды из задания приведены для осознанной очистки. В ходе подготовки лабораторной они **не запускались**.

| Команда | Назначение и последствия |
| --- | --- |
| `docker compose down -v` | Удаляет контейнер и сеть проекта, а также его именованный том с данными Studio. Выполнять только после резервного копирования и решения удалить данные. |
| `docker image rm ghcr.io/libredb/libredb-studio:latest` | Удаляет локальный образ; при следующем запуске потребуется скачать его снова. Используемый контейнером образ может не удалиться. |
| `docker ps -a` | Показывает все контейнеры; позволяет проверить отсутствие `libredb-studio`. Ничего не удаляет. |
| `docker volume ls` | Показывает тома; позволяет проверить отсутствие тома проекта после `down -v`. Ничего не удаляет. |
| `docker system prune -a --volumes` | Общая очистка Docker: удаляет остановленные контейнеры, неиспользуемые сети, образы и кэш; с `--volumes` также очищает неиспользуемые анонимные тома. Может затронуть ресурсы других проектов. Автоматически не запускать; для удаления этой лабораторной не требуется. |

Подробности: [Compose down](https://docs.docker.com/reference/cli/docker/compose/down/) и [system prune](https://docs.docker.com/reference/cli/docker/system/prune/). Именованный том этой лабораторной удаляется именно через `docker compose down -v`; глобальная очистка не является его безопасной заменой. Удаление каталога проекта из примера преподавателя не выполнялось: исходники и локальные данные пользователя сохранены.

## Демонстрация преподавателю и вывод

1. Запустите Docker Desktop и выполните последовательность запуска выше.
2. Покажите `compose.yaml`, `.env.example` и назначение постоянного тома. Реальный `.env` на демонстрации не открывайте.
3. Покажите `docker compose ps -a`, состояние `healthy`, последние строки логов без секретов и mount `/app/data`.
4. Откройте `http://localhost:3000`, введите пароль вне демонстрации экрана и покажите успешный вход администратора.
5. Объясните, что `stop` и `down` сохраняют именованный том, а `down -v` удаляет данные. Для демонстрации остановки используйте `docker compose stop`, затем `docker compose start`.

Подготовлены конфигурация оригинального LibreDB Studio, защищённые локальные переменные и воспроизводимая инструкция. Корректность конфигурации и подстановки подтверждена клиентом Compose. Практическую проверку запущенного приложения необходимо завершить после запуска движка Docker Desktop; успешное развёртывание в текущей среде не заявляется.
